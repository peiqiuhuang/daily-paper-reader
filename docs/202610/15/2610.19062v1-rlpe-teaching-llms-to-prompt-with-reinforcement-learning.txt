## Abstract 

Prompting is a widely used method for adapting general-purpose LLMs to domain-specific tasks. Effective prompts can be tedious to create manually, so prompt writing is increasingly handed to LLMs, with recent work training LLMs to write prompts for other models. These techniques either write prompts without observing how the task model behaves, blind to the failure modes the prompt should address, or must run alongside the task LLM at inference time, adding overhead to every query. Neither reflects how prompt engineering is often practiced. To close this gap, we introduce Reinforcement Learned Prompt Engineering (RLPE), which trains a model to analyze traces of a separate task model and write a prompt targeting the failures it observes. RLPE rewards the trained model strictly on prompt performance, so it learns the prompting strategies that improve the task model. The prompt is generated once and reused across the task, so inference does not require the trained model. Since RLPE needs only query access to the model it prompts, it is also compatible with closed-source models. We apply RLPE to Enigmata, BIG-Bench Extra Hard, and PlanBench. We train a 9B-parameter model that writes better prompts than state-of-the-art frontier models ( gpt-5.6-sol and 

claude-opus-5 ) and prompt optimizers (GEPA and TextGrad) on 2/3 benchmarks. Although the model is never explicitly trained to iterate on prompts, this capability emerges at a level that matches or beats frontier models. The learned prompting capability also generalizes, with the trained model improving task models 6x larger than the one it trained with, including ones from entirely different model families, and matching claude-opus-5 on a fourth benchmark held out from training. 

## 1 Introduction 

General-purpose large language models (LLMs) are adapted to specific tasks largely through prompt-ing [Liu et al., 2023], so finding effective prompts grows more valuable as LLMs take on more tasks. Automated prompt-optimization tools use LLMs to generate and search for high-performing prompts and have shown broad success [Agrawal et al., 2025, Yuksekgonul et al., 2024]. But these tools are bounded by the prompting ability of the models powering them, which remains largely understudied. Recent work has begun directly training models to write prompts. PRewrite [Kong et al., 2024], PRL [Batorski et al., 2025], and Prompt-MII [Xiao et al., 2025] train models to produce prompts from task descriptions or labeled examples. Trained this way, a model never observes the prompted model’s behavior, making it unclear what its prompts should correct. Advisor Models [Asawa et al., 2025] and Prompt-R1 [Liu et al., 2025] train a model that works alongside the prompted model, advising it on each query. Here the trained model does observe the prompted model’s behavior, but it must run with the prompted model on every query, adding inference overhead and limiting practical use. Neither captures the process of prompt engineering: inspecting outputs, spotting failure modes, and incorporating the fixes into a reusable prompt.

We introduce Reinforcement Learned Prompt Engineering (RLPE), which trains a prompt-writing model under conditions that better mirror prompt engineering practice. We train an advisor model to write prompts for a task model , the model performing the task. To write a prompt, the advisor is shown a batch of traces, each with a question the task model attempted, its response, and the response’s correctness, exposing precisely how the task model performs. The advisor generates a static prompt used for every question the task model answers, so the advisor never runs per query. During training, we run the task model with each prompt and reward the advisor by the measured performance. RLPE is practical to use. It needs only query access to the task model, so it is compatible with closed-source models (Section 5.3). Also, RLPE training is cheap, requiring modest compute and no reference prompts or LLM judges, since performance alone provides the reward. We train a 9B-parameter model via Group Relative Policy Optimization (GRPO) [Shao et al., 2024] that writes more performant prompts than state-of-the-art frontier models and prompt optimizers. It surpasses gpt-5.6-sol , claude-opus-5 , GEPA, and TextGrad on Enigmata [Chen et al., 2025a] and BIG-Bench Extra Hard (BBEH) [Kazemi et al., 2025], and matches nearly all baselines on PlanBench [Valmeekam et al., 2022] (Figure 1). These prompts are written from scratch, using only traces with no existing prompt to build on. Practitioners more often revise prompts than write new ones [Tafreshipour et al., 2025], so we evaluate iteration as a skill, in which the advisor is given a prompt to revise as well. Although prompt iteration is never directly trained, the capability emerges, with RLPE matching or beating frontier models at revising prompts (Figure 2). Training for effective prompting is far less useful without transfer beyond the task model and dataset used in training. We test the advisor along these generalization axes. Although trained with one task model, our advisor improves task models six times larger and models from other model families (Figure 4). On JustLogic [Chen et al., 2025b], a fourth, held-out benchmark, the trained model consistently beats the untrained policy and is competitive with frontier models (Table 1). These results suggest the learned prompting ability is general, not narrowly tuned to its training setup. An overview of our contributions is as follows: • We introduce Reinforcement Learned Prompt Engineering (RLPE), a training framework that mirrors prompt engineering more faithfully than previous work: an advisor model reads task-model traces, writes a prompt, and is rewarded by how well that prompt performs. • We train a 9B-parameter advisor model that beats state-of-the-art frontier models (gpt-5.6-sol and claude-opus-5 ) and prompt-optimizer tools (GEPA and TextGrad) on two out of three benchmarks. This advisor also effectively iterates on prompts, a capability that emerges without direct training and matches or exceeds frontier models. • We provide evidence that the learned prompting capability generalizes. The trained advisor improves task models six times larger than its training task model, as well as models from entirely different model families. Additionally, all trained advisors beat the untrained policy and match claude-opus-5 on a held-out benchmark not seen during training. 22 Related Work 

RL for LLMs. Reinforcement learning is now a widely used post-training method for improving targeted capabilities such as mathematical reasoning, coding, and agentic tool use [Qian et al., 2025]. Beginning with reinforcement learning from human feedback (RLHF), the field trained models toward human preferences [Ouyang et al., 2022]. More recently, focus has shifted to reinforcement learning with verifiable rewards (RLVR), which samples many rollouts per prompt and updates the model toward the highly rewarded ones [DeepSeek-AI et al., 2025]. We apply the same technique, but instead of improving a model’s own task performance, we train it to write prompts that improve the performance of a separate task model we may only be able to query. 

Prompt optimization. Prompt-optimization tools automate the search for a prompt that maximizes task performance. Early methods such as APE [Zhou et al., 2023] and OPRO [Yang et al., 2024] treat the LLM entirely as a prompt generator, sampling instructions and keeping the highest-scoring ones. More recent tools instead have the LLM read the task model’s failures and revise prompts: GEPA [Agrawal et al., 2025] uses an evolutionary approach to refine prompts, TextGrad [Yuksekgonul et al., 2024] performs gradient-descent-style optimization with natural-language feedback, and PrefPO [Singhal et al., 2026] drives revisions with pairwise preferences over outputs. These tools are only as good as the LLM behind them, which is particularly problematic because prompting ability is not often evaluated directly. We respond by measuring how well models prompt across different settings and training a model to improve that capability. 

RL for prompting. A growing line of work trains prompting models [Deng et al., 2022, Kong et al., 2024]. Some approaches train a model that steers the task model one query at a time: Advisor Models [Asawa et al., 2025] appends advice to each question, Prompt-R1 [Liu et al., 2025] runs a multi-turn agent that prompts the task model and answers itself, and others write per-instance critiques or reflections [Xie et al., 2025, Yao et al., 2023]. These approaches must run the trained model alongside the task model for every query, making it harder to scale. Other approaches avoid this per-query overhead by training a model to write one shared prompt for the task. PRL [Batorski et al., 2025] trains a prompt generator that writes prompts from just task descriptions, and Prompt-MII [Xiao et al., 2025] learns to generate instructions from labeled examples across many datasets. These approaches do not observe the task model’s behavior, hiding what the prompt must fix. Our advisor addresses both shortcomings of prior work. Its output is a standalone prompt, so the advisor is unnecessary at inference time, and its input is the task model’s traces, exposing remaining failure modes. 

## 3 RLPE: Reinforcement Learned Prompt Engineering 

3.1 Problem Statement Preliminaries. We train an advisor model , πadv , a policy that writes prompts for a separate task model based on observed traces of its behavior. The task model , πM , is a fixed language model we wish to prompt effectively; we assume only query access to it. We define a prompt p as a system prompt and a user prompt template into which a given question q is inserted. We write p(q) for the prompt with question q in place and sample responses y ∼ πM (· | p(q)) (full example prompts in Appendix A.1). Throughout our experiments, we use a baseline prompt, which keeps the system prompt empty and passes the question through unchanged as the user prompt, adding brief answer-formatting instructions when a question does not specify them (the exception is PlanBench, whose baseline is the benchmark’s official query containing the rules of the world and a one-shot example). A task is a pair (D, R ), a distribution over questions and a programmatic verifier R(q, y ) ∈ { 0, 1}

that scores a response. A trace τ = ( q, y, r ) records a question, the task model’s response to it under some prompt, and the score r = R(q, y ); we write T = {τ1, . . . , τ k} for a batch of k traces. 

Two prompt engineering settings. We divide prompt engineering into two main settings, corre-sponding to two ways of conditioning πadv : from-scratch and iterative generation. For from-scratch generation, the advisor is shown only a batch of traces T produced under the baseline prompt and must write a new prompt for the benchmark, inferring from the traces what the task model gets wrong and what instructions would fix it: 

p ∼ πadv (· | T ).

3For iterative generation, the advisor is additionally shown the prompt p currently in use, together with the corresponding traces T produced by running p, and must write a revised prompt that addresses the issues p has: 

p′ ∼ πadv (· | p, T ).

Separating prompt engineering into these two settings aligns our setup with real practice, where practitioners both generate new prompts and iterate on existing ones. 

Objective. Both settings share a single goal: produce a prompt p that performs as well as possible on the benchmark, that is, that maximizes

## 4 Experimental Setup 

4.1 Data 

We use three benchmarks across model capabilities for training: BBEH (multi-step reasoning prob-lems), Enigmata (various self-contained puzzles), and PlanBench (block-stacking plan-generation questions). We additionally evaluate on JustLogic (deductive logic reasoning problems) as a held-out benchmark never seen during training. We selected benchmarks against two criteria. First, each bench-mark must be reasoning-sensitive, showing large accuracy gains when increasing gpt-oss-20b ’s reasoning effort from low , since we believe most of a prompt’s effect is guiding reasoning (full details in Appendix B.1). Second, each benchmark must provide a programmatic verifier, which keeps grading cheap and fast for the many prompt evaluations training requires. We split BBEH’s original data into train, validation, and test sets. For Enigmata and PlanBench we add synthetic examples from the benchmarks’ official generators 1 to the original data. This extra data is needed because our prompt-sensitivity filtering, applied only to the training data, requires more raw questions than the benchmarks provide. For PlanBench, we train on its official plan-generation task but evaluate on its official optimal-planning variant, defined over the same questions but additionally requiring plans to be as short as possible, which resolves an ambiguity in the original task (Appendix B.5). For JustLogic, which serves only as a held-out generalization test, we draw traces from the benchmark’s official train split and score on a stratified sample of its official validation split. Exact splits for every benchmark are listed in Appendix B.2. 

Prompt-sensitivity filtering. Many benchmark questions are insensitive to prompting, meaning the task model answers them correctly, or fails them, regardless of the prompt provided. These questions provide no training signal, so we filter them out of the training data, leaving the validation and test splits untouched. To identify them, we ran high-performing and low-performing prompts over the data and kept only the questions answered correctly more often under the high-performing prompts. For some benchmarks this cut the training data by up to 50% (full details in Appendix B.4).

4.3 Training Setup Training configuration. We train a separate advisor per benchmark with GRPO (LoRA rank 32, learning rate 3 × 10 −5, KL penalty 0) for 50 steps with 32 groups per step and 8 rollouts per group, totaling 12,800 rollouts. The trained model generates up to 32,768 tokens at temperature 1.0 per rollout. Each rollout shows the advisor k = 10 traces and instructs it to create a new prompt (full instructions in Appendix A.2). The traces are generated with the baseline prompt. We settled on ten traces as an intentional tradeoff: enough for a reliable read on prompt performance, but few enough that the method stays usable in low-data settings. Training and inference ran on NVIDIA B200 GPUs (full compute details in Appendix B.6). 

Reward. Rollouts are rewarded by Acc T (p), as defined in Section 3.2; a misformatted output from the trained policy receives a fixed reward of −0.1.

4.4 Baseline Configurations Frontier models. gpt-5.6-sol and claude-opus-5 are passed the same instructions used during training, at medium reasoning effort and default temperature, with a 32,768-token output cap. 

Untrained policy. We run the qwen-3.5-9b base model with the same instructions used during training, at medium reasoning effort and temperature 1.0. 

GEPA. GEPA is an evolutionary prompt optimizer that leverages an LLM to read the task model’s failures and propose a revision [Agrawal et al., 2025]. We run it at its highest optimization budget (auto="heavy" ) with default parameters otherwise. 

TextGrad. TextGrad casts prompt optimization as gradient descent in natural language, using LLMs to produce textual feedback on the current prompt’s failures and apply it as an update [Yuksekgonul et al., 2024]. We run with default parameters. Both GEPA and TextGrad use gpt-5.6-sol at medium reasoning effort with a 32,768-token cap as the LLM powering the optimization. The final prompt for each is selected as the highest-scoring candidate on the full validation set (full details in Appendix B.3). This feedback is unavailable to the advisor models, making the optimizers particularly well-resourced baselines. 

4.5 Evaluation Prompt optimizers. Each optimizer’s best-performing prompt is scored on the test set. 

Advisor models. For each benchmark, we draw B = 10 batches each with k = 10 traces from the validation set. In the from-scratch setting, each advisor model receives one batch at a time with the same instructions used during training, and writes one prompt per batch (full from-scratch instructions in Appendix A.2). We score the B prompts on the test set and report their mean accuracy. In the iterative setting, each advisor model additionally receives an initial prompt to revise in its instructions, together with the traces the task model produced under that prompt (full iteration instructions in Appendix A.3). We again report the mean test-set accuracy of the B revised prompts. ## 5 Results 

We train three advisor models with RLPE, one each on Enigmata, BBEH, and PlanBench. The following sections evaluate them in the from-scratch and iterative settings and test generalization. 

5.1 From-Scratch Setting Setup. We compare the trained advisor against the untrained qwen-3.5-9b policy, the frontier models, and the prompt optimizers in the from-scratch setting across all three datasets, following the protocol in Section 4.5, with the baseline prompt as a reference point. 

Results. Figure 1 shows RLPE more than doubles the untrained policy’s gains over the base-line prompt on every benchmark (16.8 vs. 5.5 points on Enigmata, 12.2 vs. 4.4 on BBEH, and 41.4 vs. 17.1 on PlanBench). RLPE beats frontier models on Enigmata (0.516 RLPE vs. 0.448 

gpt-5.6-sol and 0.414 claude-opus-5 ) and BBEH (0.275 RLPE vs. 0.230 gpt-5.6-sol and 0.222 claude-opus-5 ). On both benchmarks, RLPE also beats the prompt optimizers, even though they select their strongest prompt on the validation set. On PlanBench, the trained advisor is competi-tive with gpt-5.6-sol and both prompt optimizers (0.466 RLPE vs. 0.435 gpt-5.6-sol , 0.508 GEPA, and 0.515 TextGrad), though claude-opus-5 remains clearly ahead (0.581). 

5.2 Iterative Setting Setup. While the from-scratch setting has the advisor write a prompt from traces alone, the iterative setting also gives it a starting prompt to revise and the traces produced by running that prompt. We evaluate this capability with two experiments. The first experiment gives every advisor model the same starting prompt, so that each model’s iteration ability can be compared directly. We use the untrained qwen-3.5-9b policy’s ten from-scratch prompts from Section 5.1 as starting prompts. We choose these prompts because they are genuine attempts at improvement, so gains over them are not trivial. Still, the from-scratch results show more effective prompts exist, so headroom remains for further improvement. Each starting prompt is run on the same questions as the from-scratch experiment, producing fresh traces of the starting prompt’s performance. Each advisor model then produces a revised prompt, and we report the mean gain over the starting prompt’s score across the ten batches. We run this experiment on Enigmata and BBEH only, since one of the untrained policy’s ten PlanBench generations in the from-scratch experiment failed to parse, leaving no valid starting prompt for that batch. 6Figure 3: Self-iteration results in limited gains. Each advisor model revises its own ten from-scratch prompts. Light bars = starting prompts’ mean score (from Figure 1); dark bars = revisions’ mean score, with SE bars. No advisor model gains more than 3 points on any benchmark, except the untrained policy on PlanBench (+9), whose weak starting prompts leave more headroom. In the second experiment, each advisor model revises its own prompts. This tests whether gains can compound when a model is applied to its own output. We take a model’s ten from-scratch prompts, rerun them to collect fresh traces, and give each prompt and its traces back to the same model for a revised prompt. We report the mean test-set scores of the ten revisions. 

Results. In the first experiment, where every advisor model revises the same starting prompt, the trained advisor shows the largest performance gains (Figure 2). On Enigmata the trained advisor more than triples every other model’s gain (+9.6 RLPE vs. +2.8 gpt-5.6-sol and +2.0 claude-opus-5 ), while on BBEH it is competitive with the frontier models (+4.7 RLPE vs. +4.4 gpt-5.6-sol and +4.2 claude-opus-5 ) but still much better than the untrained policy (+1.3). In the second experiment, models gain little from revising their own prompts. The gains for almost all advisor models are under 3 points on every benchmark (Figure 3). The exception is the untrained policy on PlanBench, which improves its weak starting prompts by roughly 9 points.

## 6 Discussion and Limitations 

Prompt-writing is a learnable skill. With no custom dataset and relatively low compute, we trained a 9B-parameter advisor that writes better prompts than far larger frontier models gpt-5.6-sol and 

claude-opus-5 on two of our three benchmarks. The trained advisor also beats the prompt optimizer tools on these two benchmarks, even with these tools leveraging frontier model and selecting for the best prompt by evaluating on the validation set. The trained advisor is also the strongest prompt editor, improving the same prompt by three times as much as either frontier model, without ever being trained to revise prompts. These results reflect that writing prompts for another model is a trainable skill, one that today’s frontier models have not saturated. The prompting ability of models has received little direct study, especially for the most recent frontier models, making these results among the first direct measurements of this capability and pointing to meaningful room for improvement. 

The learned skill shows signs of generalization. Multiple results indicate the advisor learns a general prompt-writing skill rather than one tied to its specific training environment. In addition to prompt iteration emerging without direct training, the three trained policies are all competitive with claude-opus-5 on the held-out JustLogic benchmark while clearly beating the untrained policy. Beyond datasets, the skill transfers across task models. Despite training with a single one (gpt-oss-20b ), the advisor improves task models six times larger and models from other model families. The advisor even shows gains on gpt-5-nano , demonstrating the approach extends to closed-source models. Still, the skill transfer is not perfect. Limitations. As one of the few works on training models to write prompts, we deliberately kept each training run minimal, training on a single prompting setting, a single benchmark, and a single task model. This let us isolate the effects of training and study its generalization. We see joint training on both settings (from scratch and iterative), multi-benchmark training, and training against multiple task models as natural extensions. Our benchmarks are also all single-turn tasks with programmatic verifiers. We hope to study multi-turn and more agentic tasks, including open-ended ones graded by an LLM judge. Finally, as noted above, our results are not uniformly strong, with the advisors trailing stronger baselines on PlanBench and JustLogic. We expect these gaps to narrow with more training and larger advisor models. 

## 7 Conclusion 

Using RLPE, we trained a 9B-parameter advisor model that beats or is competitive with state-of-the-art frontier models and prompt optimizer tools across multiple benchmarks. The advisor also improves far larger task models than it trained with, and transfers to a held-out benchmark. RLPE achieves this by modeling prompt engineering more faithfully than prior work, rewarding the advisor for the performance of prompts written from observing the task model’s behavior. Our framework is also easy to apply. Training needs only modest compute and the task dataset itself, since reward is computed directly from performance, and the advisor writes a prompt from just ten traces, remaining useful when data is scarce. We see this work as particularly timely because progress in AI systems increasingly comes from orchestrating multiple models, and prompting is a critical part of that orchestration. Our results may suggest this capability remains underdeveloped in current models, with substantial headroom even for frontier models. There are many interesting variations on the RLPE recipe, including adding more prompting tasks, extending the reward beyond task accuracy to incorporate cost or latency, and more intelligently sampling the traces the advisor sees. 9References

B.1 Reasoning-Effort Sensitivity 

To measure each benchmark’s sensitivity to reasoning, we ran gpt-oss-20b with the baseline prompt over each benchmark’s training data at each reasoning effort, recording accuracy and the average output tokens per question (Figure 5). We selected benchmarks where increased reasoning effort produced a large accuracy gain, roughly 10–15 points or more. At high reasoning effort the model often reasoned for longer than the maximum output its context length allows, truncating its responses, so we omit high measurements for some benchmarks.

B.4 Prompt-Sensitivity Filter 

For each benchmark, we assembled a small set of high-performing prompts identified during pre-liminary experimentation, and a small set of low-performing prompts consisting of the baseline prompt and weaker prompts from the same experimentation. We then ran five to six runs of the training questions under each set. For a question q, let phigh (q) and plow (q) denote the fraction of high-performing and low-performing runs in which the task model answered q correctly. A question 23 is kept only if 

phigh (q) > p low (q),

that is, if the better prompts actually help on it. Questions the task model always answers correctly or always fails are removed automatically by this rule, since both fractions tie. The filter uses training data only; the validation and test sets are left in each benchmark’s natural distribution. 

B.5 PlanBench Optimal-Planning Evaluation 

PlanBench [Valmeekam et al., 2022] poses block-stacking problems. Each question gives an initial arrangement of blocks and a goal arrangement, and the model must produce a sequence of pick-up, put-down, stack, and unstack actions that reaches the goal. The benchmark defines several official tasks over the same questions. Its plan-generation task accepts any valid plan and leaves it ambiguous in the instructions whether a plan longer than necessary is penalized. The frontier advisor models discovered that it is not penalized. Many of their prompts instruct the task model to unstack every block onto the table and then rebuild the goal arrangement from scratch, a procedure that is valid for any instance but far longer than necessary; one such prompt states directly that “extra moves cost nothing – only legality and the final goal matter.” The qwen-3.5-9b -based advisors never discovered this exploit, and many of the trained advisor’s prompts instead push the task model toward minimal plans. We did not catch this ambiguity until after training, so the advisor was trained on the plan-generation task. For evaluation we instead use PlanBench’s official optimal-planning task, which poses the same questions with the ambiguity resolved. Its question text attaches a one-minute cost to every action in the plan and asks the model to minimize the total time taken, and its grader accepts a plan only if it is valid and matches the certified optimal plan length. We view this as the fairer comparison, since it fixes the ambiguity in the task itself rather than rewarding whichever advisor happened to guess the grader’s behavior. Figure 6 shows the test results under both tasks, with each advisor model writing its prompts from traces of the corresponding task. The ordering is largely unchanged, but the frontier models drop the most once optimality is enforced ( gpt-5.6-sol −23 .0 and claude-opus-5 −20 .3

points, against −15 .9 for RLPE).

B.6 Compute Details 

All training, and all inference for the advisor and task models, ran on NVIDIA B200 (180 GB) GPUs on Fireworks AI (cloud); frontier prompt writers used as advisor models or within a prompt optimizer were accessed through their native APIs. Each training run used five B200s in total: a two-GPU 24 trainer that holds and updates the 9B advisor, a single-GPU deployment serving the current advisor snapshot for rollout sampling, and two single-GPU deployments serving gpt-oss-20b for rollout grading. A 50-step run completes in 9–14 hours of wall-clock time for each of Enigmata, BBEH, and PlanBench. Evaluation used one to seven additional single-GPU B200 deployments serving the task model, plus a single-GPU deployment serving each qwen-based prompt writer.
