Abstract 

Harness optimization improves LLMs by refining reusable prompts and scaffolding, yet requires further adaptation for pro-gram generation tasks such as text-to-SQL and text-to-Python. Existing methods of-ten rely on LLM reflectors to propose har-ness updates, which can fix observed fail-ures but also disrupt previously correct be-havior. Text-to-code tasks offer a natural way to mitigate this issue: we can execute generated outputs, allowing us to evalu-ate and verify the effects of proposed up-dates directly. Building on this signal, we introduce HERO (Harnessing Evidence for Refinement and Optimization), which combines offline and test-time harness opti-mization. At the first stage, HERO learns reusable prompt updates from execution-verified successes and failures and validates candidate revisions before adoption. At test time, we treat the generated code as an instance-specific harness and refine it us-ing execution feedback. Across four SQL, Cypher, and Python benchmarks, HERO achieves the best offline performance, im-proving pass@1 by 7.6 points over the initial prompt, while test-time refinement adds another 2.0 points and improves exe-cution efficiency. 

1 Introduction 

LLM agents are increasingly employed to inter-act with external environments through tools, often by generating executable programs such as SQL and Cypher queries and Python func-tions (Li et al., 2023; Schick et al., 2023; Feng et al., 2025; Zhuo et al., 2025; Ouyang et al., 2026). These artifacts provide a flexible inter-face for models to perform computation and in-teract with external systems (Gao et al., 2023;

Wang et al., 2024). Their quality depends not only on the underlying model, but also on the surrounding harness —the prompts, tools, and memory that shape generation (Khattab et al., 2024; Lee et al., 2026; Li et al., 2026; Lopopolo, 2026). This makes the harness a natural target for improving LLM agent performance. Ac-cordingly, existing work has pursued two re-lated directions: optimizing reusable harness components across tasks (Lee et al., 2026; Lin et al., 2026; Yang et al., 2026; Agrawal et al., 2026), and using test-time feedback to select or refine generated outputs (Ni et al., 2023; Chen et al., 2024; Madaan et al., 2023). Improving program generation through these directions presents two linked challenges. First, reusable updates must correct recur-ring errors without degrading behavior that al-ready works. LLM-generated feedback can be unreliable without external grounding (Huang et al., 2024; Kamoi et al., 2024), and prompt revisions that resolve failures can introduce re-gressions on previously successful cases (Wu et al., 2024b). The challenge is therefore to derive grounded diagnoses of what to change and preserve from execution outcomes, and translate these diagnoses into reusable guid-ance. Second, this general guidance must be complemented by feedback specific to the cur-rent instance. An optimized prompt captures strategies learned across training tasks, but a generated program may still encounter errors that require observations from its own execu-tion. Approaches such as Dynamic Cheatsheet (DC) and ACE accumulate experience through evolving shared contexts (Suzgun et al., 2026; Zhang et al., 2026). When shared context is updated at test time, unreliable or overly spe-cific feedback can become persistent guidance, allowing errors from one instance to affect sub-sequent tasks. Together, these challenges mo-1arXiv:2610.19184v2 [cs.CL] 17 Oct 2026 tivate grounding offline harness updates in ex-ecution evidence while keeping test-time cor-rections local to the current program. To address these challenges, we introduce 

HERO (Harnessing Evidence for Refinement and Optimization), a two-level framework that grounds reusable guidance updates in ex-ecution evidence and confines test-time adap-tation to the current program. Our contribu-tions are threefold: • A unified two-level formulation. We formulate program generation as a two-level optimization problem that couples offline prompt optimization with test-time refinement of instance-specific pro-grams. • Execution-grounded feedback and verification. Offline, we use execution evidence from successful and failed pro-grams under prior prompts to identify what to correct and preserve. At test time, execution feedback and retrieved verified training examples guide program revisions, which are accepted only when supported by evidence. • Empirical evaluation and analysis. 

We demonstrate correctness gains over ex-isting offline harness optimizers across di-verse query-generation and programming tasks, with further improvements from test-time refinement. We further evaluate execution efficiency and computational cost, finding that the learned prompts re-main compact across tasks. 

2 Related Works 

Prompt and harness optimization. 

Prompt and harness optimization improves frozen LLMs by adapting reusable compo-nents around them. MIPRO (Opsahl-Ong et al., 2024) jointly optimizes instructions and few-shot demonstrations using task-level feedback. Reflection-based approaches in-clude GEPA (Agrawal et al., 2026), which uses trajectory feedback to propose prompt revisions, and STRAGO (Wu et al., 2024b), which derives refinement strategies from both successful and failed examples to mitigate prompt drift. Other approaches broaden the optimization target: ACE (Zhang et al., 2026) maintains an evolving context through generation, reflection, and curation; SkillOpt (Yang et al., 2026) optimizes reusable textual skills; and Meta-Harness (Lee et al., 2026) searches over harness implementations using source code, scores, and execution traces. Building on this line of work, HERO adopts a similar offline optimization loop but enriches reflection with execution feedback from suc-cessful and failed programs generated under prior prompt revisions, aiming to improve program generation while limiting regressions. 

Test-time refinement. Test-time methods refine model outputs using feedback avail-able during inference. ReAct (Yao et al., 2022) interleaves reasoning, actions, and en-vironment observations, while Reflexion and related self-refinement methods use feedback from earlier attempts to revise subsequent outputs (Shinn et al., 2023; Madaan et al., 2023). Dynamic Cheatsheet (DC) (Suzgun et al., 2026) further accumulates self-curated strategies across queries through persistent memory. These methods emphasize adapta-tion from test-time experience. HERO com-plements this adaptation with reusable guid-ance learned through offline prompt optimiza-tion. The optimized prompt remains fixed dur-ing inference, while execution feedback and re-trieved, verified training examples guide refine-ment of the current program.

4.1.1 Textual Gradients from Execution-grounded Experience 

Prompt optimization can be viewed as a dis-crete analogue of gradient-based optimization, where natural language critiques or reflections serve as “textual gradients” for prompt up-dates (Pryzant et al., 2023; Yuksekgonul et al., 2024). Prior work uses LLM reflection to guide prompt updates (Pryzant et al., 2023; Lin et al., 2026; Agrawal et al., 2026), but such feedback can be unreliable without ex-ternal grounding (Huang et al., 2024; Kamoi et al., 2024). Following Wu et al. (2024b), we use both successful and failed cases but en-rich reflection with execution outcomes and traces from programs generated under prior prompt revisions to identify what to correct and preserve. This connects prior edits to ob-served program behavior, providing concrete context for diagnosing what to correct and pre-serve. 4.2.1 Two Sources of Refinement Evidence 

Refinement draws on two complementary sources. Execution evidence includes execu-tion traces, runtime errors, returned outputs, and environment probes that help identify instance-specific problems. Retrieved demon-stration evidence consists of execution-verified training examples that provide implementa-tion patterns, such as library-specific conven-tions, that execution feedback alone may not reveal. The refiner combines environment interac-tion and execution-based program refinement (Yao et al., 2022; Chen et al., 2024) with instance-specific demonstration retrieval. Un-like MIPROv2, which selects demonstrations during offline optimization (Opsahl-Ong et al., 2024), we select demonstrations separately for each test instance. Specifically, we retrieve up to 𝑛 verified training examples using lexical similarity, then let the refiner select at most three relevant demonstrations.

5 Experimental Setup 

5.1 Benchmarks 

We evaluate on four text-to-function genera-tion benchmarks spanning SQL, Cypher, and Python generation. 

BIRD-SQL (Li et al., 2023). BIRD-SQL evaluates text-to-SQL generation over realis-tic SQLite databases from diverse application domains. Given a natural-language question, database schema, and optional external knowl-edge, the model generates an executable SQL query. 

CypherBench (Feng et al., 2025). Cypher-Bench evaluates text-to-Cypher generation over large-scale Neo4j property graphs derived from Wikidata, covering query patterns such 5as multi-hop retrieval, aggregation, compari-son, and temporal reasoning. 

BigCodeBench-Instruct (Zhuo et al., 2025). BigCodeBench-Instruct evaluates text-to-Python function generation from text instruction across diverse programming and library-use tasks. 

DSCodeBench (Ouyang et al., 2026). 

DSCodeBench evaluates text-to-Python func-tion generation for practical data-science tasks spanning ten widely used libraries. For each benchmark, we construct a diag-nostic set 𝒟 diag to provide examples and exe-cution feedback for prompt optimization, and an update set 𝒟 upd to evaluate candidate re-visions. For final harness selection, we use a separate set 𝒟 sel where dataset size permits; otherwise, we reuse 𝒟 upd . 6.4 Execution Efficiency 

For SQL queries and Python code, correctness alone does not fully capture solution quality: programs that produce the same correct result can differ substantially in execution cost (Li et al., 2023). We therefore report VES along-side pass@1 to assess whether improvements in correctness also preserve execution efficiency. As shown in Table 3, HERO-O achieves the highest mean VES on three of four bench-marks: BIRD-SQL (91.9 ), BigCodeBench (75.0 ), and DSCodeBench ( 57.8 ). Together with the corresponding pass@1 gains, these re-8sults indicate that the improved correctness on these tasks is not achieved at the expense of execution efficiency. On CypherBench, Skil-lOpt attains the highest mean VES ( 137.7 ), though with substantial variability across runs (SD 50.8 ). With HERO-T, VES further im-proves on BIRD-SQL, BigCodeBench, and DSCodeBench, alongside the corresponding gains in pass@1. On CypherBench, however, pass@1 increases from 85.5 to 89.93 , while VES decreases from 109.8 to 101.7 . This diver-gence highlights a correctness–efficiency trade-off: test-time refinement solves more instances, but the resulting programs are less efficient un-der VES. Overall, HERO delivers concurrent gains in correctness and execution efficiency on three of four benchmarks, demonstrating that its performance improvements generally extend beyond accuracy alone.

7 Conclusion 

In this work, we introduced HERO, a two-stage harness framework for program genera-tion that combines grounded offline prompt optimization with evidence-grounded test-time refinement. Across four SQL, Cypher, and Python benchmarks, HERO consistently outperforms the initial prompt and existing prompt optimization baselines, with test-time refinement providing further gains on every benchmark. Our analyses show that execution-grounded updates reduce regressions during optimization, while the learned prompts re-main compact and robust across optimization settings. Together, these results support com-bining reusable cross-task optimization with instance-specific refinement for more effective program generation. 

Limitations 

Budgeting and computational cost. Our evaluation uses fixed, benchmark-specific bud-gets, which may limit the gains that some methods could achieve with longer searches. Substantially expanding these budgets is com-putationally demanding: even under the eval-uated budgets, ACE and Meta-Harness re-quire approximately 12 and 24 hours of wall-clock time, respectively, on BigCodeBench in our setup. To support controlled comparisons within these practical constraints, we use task-rollout counts as a common measure of eval-uation effort and match budgets as closely as method-specific procedures permit. This mea-sure, however, does not fully capture differ-ences in the costs of reflection, candidate gen-eration, and selection. Nevertheless, we have sought to make the comparisons as fair and 9transparent as possible within these computa-tional and methodological constraints. 

Model dependency. Our main evaluation relies on proprietary GPT-5 and GPT-5.4 models, whose future updates or deprecation may affect exact harness reproducibility. How-ever, HERO operates entirely at the harness level and does not require access to or modi-fication of model weights, allowing the same optimization procedure to be applied to other compatible backbones. Learned prompts may still require re-optimization when the underly-ing model changes.

Here, we provide additional details on each benchmark and our preprocessing and split-ting procedures. Three conventions apply across all datasets. First, all splits are con-structed once using a fixed dataset-level seed before any experiment, and pool membership is held fixed across methods and run seeds. BIRD-SQL (Li et al., 2023). BIRD-SQL is a large-scale text-to-SQL benchmark de-signed to evaluate SQL generation in real-istic database settings, where models must reason over database contents in addition to schemas. It contains 12,751 natural-language– SQL pairs across 95 SQLite databases and 37 application domains: 9,428 training exam-ples over 69 databases, 1,534 development ex-amples over 11 databases, and 1,789 exam-ples over 15 databases in a concealed test set. Among the training and development databases, 32% originate from Kaggle, 48% from the CTU Prague Relational Learning Repository, and the remaining 20% from other publicly available tables. Each instance in-cludes a natural-language question, a refer-ence SQL query, the associated database, and optional expert-annotated external knowledge. The development set spans three difficulty levels: 925 simple, 465 moderate, and 144 challenging examples, categorized based on question understanding, external knowledge requirements, database complexity, and SQL complexity. BIRD also evaluates execution ef-ficiency, enabling assessment of both correct-ness and runtime behavior. 

Preprocessing and splits. Following StreamBench (Wu et al., 2024a), we use the official TRAIN split for optimization and the official DEV split for evaluation, both downloaded from 2; the concealed test set is not used. To evaluate cross-database transfer, we partition TRAIN at the database level. We reserve 14 of the 69 training databases for final prompt selection, sampling at most 100 questions per database. Of the remaining 55 databases, 15 are reserved exclusively for the update pool, from which we sample 250 ques-tions, while the 500-question diagnosis pool is sampled from the remaining 40 databases with every database represented. Thus, the diagnosis, update, and selection pools are disjoint at the database level. Before sampling, we exclude examples whose reference queries fail to execute or re-turn empty results. For final evaluation, we use the 1,534 DEV examples and exclude four whose reference queries fail under our evalua-tor, yielding 1,530 scored examples. Correct-ness is determined using the official execution-accuracy comparator: predicted and reference outputs are compared as sets of tuples, ignor-ing row order and duplicates while preserving column order.

Implementation details. C.1 Offline Prompt Optimization 

We run 𝑇 = 5 optimization rounds with no early stopping. In each round, we evaluate the current prompt on the full diagnosis set and uniformly sample 32 incorrect and 32 cor-rect examples. For incorrect examples, the re-flector receives the task input, generated out-put, failure category, evaluator feedback, and available reference information; correct exam-ples are included to identify behaviors that should be preserved. The optimization con-text also includes aggregate failure statistics and complementary feedback from the previ-ous round. Based on this information, the re-flector independently proposes four candidate prompt revisions, with up to eight edits per candidate. Proposals are rejected if they can-not be parsed, leave the prompt unchanged, or introduce task-specific values or identifiers found only in reference solutions. 

Candidate evaluation and acceptance. 

In each optimization round, we compare four candidate prompts with the current prompt us-ing adaptive paired evaluation (Algorithm 2). All candidates are initially evaluated on the same 50 examples from the 250-example up-date set, with a budget of two additional 50-example pulls allocated by the algorithm. Can-didate scores are paired improvements in ex-ecution accuracy, macro-averaged across ob-served databases or domains. Standard errors are computed from the sample standard devia-tion of group means divided by the square root of the number of observed groups, floored by the pooled row-level standard error with min-imum per-row variance 0.02 . We set 𝑧 = 1 

for evaluation allocation and early stopping, but accept an update only if the best candi-date’s estimated mean improvement exceeds 

𝜏 = 0.01 . Accepted prompts and any addi-tional candidates exceeding this threshold are archived for final selection. 

Final selection. After five optimization rounds, we select the final prompt through a second adaptive race over the archive, with a budget equal to 75% of the evaluations needed to score every archived prompt on the full se-lection set. 

C.2 Test-Time Refinement 

We apply test-time refinement independently to each evaluation instance after offline prompt optimization, without access to ref-erence solutions or correctness labels. Each episode starts from the initial output gener-ated by the selected offline prompt; therefore, 

𝐵 = 0 recovers the corresponding unrefined prediction. Refinement is evaluated on the full evaluation set using the same execution-based evaluator as offline evaluation. 

Tools and interaction budget. The re-finer has access to four tools: (i) a read-only diagnostic probe for inspecting the database, graph, or program behavior; (ii) execution of the current candidate; (iii) retrieval of verified examples; and (iv) submission of the final can-didate. We use an interaction budget of 𝐵 = 3 ,counting diagnostic, execution, and retrieval actions; final submission does not consume the budget. Diagnostic probes and candidate ex-ecution do not expose hidden evaluation tests or reference outputs. 

Verified-example retrieval. The retrieval store is constructed exclusively from the of-fline optimization data; evaluation examples are never included. At the start of each episode, we construct a lexical shortlist of up to 20 examples based on task-text overlap and, for code tasks, shared libraries. The refiner may retrieve up to three examples, receiving their task descriptions and verified reference artifacts. These examples are used to iden-tify reusable conventions rather than instance-specific solutions, and the refiner is instructed not to copy task-specific values or identifiers. 

Refinement and verification. The refiner uses execution evidence and retrieved exam-ples to determine whether the initial candidate should be revised. Retrieval-based revisions require consistent evidence for a relevant con-vention, while execution-based revisions must be supported by observations from the current 17 instance. Any revised candidate must execute successfully before submission. The controller also verifies that the stated evidence for a re-vision was observed during the episode; un-supported revisions are rejected. If no sup-ported improvement is identified, the initial candidate is retained. The ReAct baseline in Section B uses the same interaction framework without verified-example retrieval or evidence-based acceptance.

D.1 Token Consumption and prompt length 

Table 5 compares methods along two dimen-sions: average tokens per LLM call during optimization and final prompt length, which affects recurring inference costs. ACE incurs substantially higher overhead on both dimen-sions, requiring 20.8–38.5K tokens per opti-mization call and producing playbooks of 17– 53K tokens (8–38 × longer than those of other methods). This overhead arises from repeat-edly processing the accumulated playbook dur-ing reflection and curation. In contrast, the remaining methods generally require 1.8–3.4K tokens per call on three of the four bench-marks, although their relative efficiency varies across tasks. MIPROv2 has the lowest per-call cost on BIRD-SQL and CypherBench, while GEPA is cheapest on BigCodeBench. How-ever, MIPROv2’s cost increases to 7.5K tokens per call on DSCodeBench, with a 6.4K-token final prompt, due to lengthy bootstrapped demonstrations. Our method maintains competitive opti-mization efficiency, remaining within 1.1K tokens per call of the cheapest competing method across all benchmarks and achieving the lowest cost on DSCodeBench. Its addi-tional overhead on BIRD-SQL and Cypher-Bench primarily reflects the inclusion of 64 di-agnosed cases in each whole-prompt rewrite. Importantly, our final prompts remain com-pact (1.4–2.5K tokens), achieving the short-est length on DSCodeBench and remaining within 2× of the shortest prompts elsewhere. Prompt lengths are also stable across seeds (e.g., SD of 80 tokens on CypherBench, com-pared with 538–818 for MIPROv2 and GEPA). Since prompt length contributes to the input-token cost of each downstream query, these results indicate that the performance improve-ments in Table 1 are achieved without substan-tially increasing the shared prompt overhead at inference time.

D.3 Model Generalization Results on GPT-5.4 To assess generaliza-tion across model backbones, we extend our evaluation to GPT-5.4 on all four benchmarks.
