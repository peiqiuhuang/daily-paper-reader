LLM agents retrieve untrusted content and act through tools, creating indirect prompt-injection risks that can cause unauthorized actions or persistent state changes. Existing automated red-teaming largely optimizes payloads for pre-specified scenarios, leaving latent vulnerabilities across the agent’s behavior space unexplored. We present ASPIRE, an Agentic Safety & Prompt Injection Red-teaming Engine for open-ended, behavior-level vulnerability discovery. ASPIRE maintains an evolving Agent Security Behavior Graph and uses complementary Explore and Exploit experts to discover, verify, and generalize consequence-centric tests. Trajectory evidence updates the graph and diagnoses partial or failed attempts, while cross-run memory transfers useful red-team strategies. Experiments on various benchmarks show that ASPIRE substantially expands coverage across consequences, injection methods, environments, and behavior paths while maintaining strong attack success. 

## 1. Introduction 

LLM agents are evolving from conversational interfaces into systems that act on the world (He et al., 2026a; Wang et al., 2024; Zhou et al., 2024). They retrieve external content, invoke tools, and modify software repositories and financial records. Protocols such as MCP (Anthropic, 2025) and A2A (Agent2Agent Project Community, 2025) further expand this reach by standardizing access to external resources and services. This growing reach also expands the agent’s trust boundary: an instruction embedded in an email, webpage, or attachment can enter the agent’s context as data, be interpreted as intent, and ultimately be executed with the agent’s privileges (Greshake et al., 2023; He et al., 2025; Zhan et al., 2024). The resulting vulnerability is therefore a property of the behavior path that carries untrusted content to a privileged outcome, not of the injected string alone.

Such vul-nerabilities are often latent: they become ob-servable only when adversarial content enters a particular workflow and propagates through the agent’s decision process. We view an agentic prompt-injection vulnerability as an exploitable influence path through which untrusted content enters an agent workflow, affects its intermedi-ate decisions, and reaches an unintended action or state change. Discovering such vulnerabili-ties therefore requires more than producing a successful payload: red-teaming must uncover the structure and boundaries of the agent’s vul-nerability space, including how attacker influence propagates through its workflow and where it is blocked. Benchmarks pair user tasks with predefined malicious goals and injection cases (Debenedetti et al., 2024; Li et al., 2026), while black- and grey-box methods optimize injection content after the target consequence and environment are fixed (Wang et al., 2025a; Zhang et al., 2026). Agent builders instead need open-ended vulnerability discovery :systematically searching across consequences, environments, injection methods, and trigger conditions to uncover diverse exploitable paths throughout an agent’s workflow. To support this broader form of red-teaming, we present ASPIRE, an Agentic Safety & Prompt Injection Red-teaming Engine for automatically discovering and diagnosing prompt-injection vulner-abilities in LLM agents. ASPIRE follows the workflow of a security scientist: it forms hypotheses about a target agent, tests them through controlled experiments, and updates its understanding from the resulting evidence. Central to this process is an Agent Security Behavior Graph , an evolving, evidence-backed model of how attacker-controlled information may flow from external environments, through the agent’s retrieval and reasoning processes, to downstream actions or state changes (Section 3.2). The graph organizes plausible behavior paths and records evidence that supports, qualifies, or blocks them. It does not attempt to reconstruct the agent’s ground-truth internal computation; instead, it represents the red-teamer’s current empirical knowledge of the target’s security behavior. ASPIRE begins with static reconnaissance over the agent’s role, tools, and environmental interfaces to initialize the behavior graph and seed plausible consequences and injection methods (Section 3.1). It then conducts iterative discovery using two complementary experts: the Explore expert searches for novel vulnerabilities and expands the exploration frontier across the agent’s attack surface, while the 

Exploit expert verifies and generalizes discovered ones. Guided by the graph, they propose red-team test skeletons over candidate behavior paths, injection environments, methods, and intended consequences (Section 3.2). A separate realizer converts each skeleton into an executable test by generating a concrete injection payload and a trigger user query, keeping vulnerability search distinct from payload optimization. Each test is executed and evaluated using trajectory evidence, which updates the graph and guides the next round. Across runs, ASPIRE further distills important search decisions into 

strategy memory (Section 3.4), allowing future experts to reuse transferable red-team experience rather than specific attacks. In summary, we illustrate the following key contributions: • We reframe agentic prompt-injection red-teaming from injection payload optimization to open-ended vulnerability discovery , systematically uncovering and mapping multi-step influence paths, reachable consequences, and behavioral vulnerabilities. • We develop ASPIRE, an autonomous framework grounded in an evolving Agent Security Behavior Graph . ASPIRE orchestrates dual Explore-Exploit experts over structured red-team tests, and distills transferable lessons into cross-run strategy memory. • Across diverse benchmarks and models, ASPIRE consistently uncovers deep vulnerabilities (∼ 50% ASR) with near-complete surface coverage (98 .4% tools and 100% environments) at affordable cost ( ≤$2.00/vuln). 

## 2. Related works 

Agentic prompt-injection attacks and defenses. Indirect prompt injection exploits untrusted content retrieved by an agent to redirect its decisions and tool use. Benchmarks such as InjecAgent (Zhan et al., 2024), AgentDojo (Debenedetti et al., 2024), and AgentDyn (Li et al., 2026) established this threat in tool-integrated agents, while WASP (Evtimov et al., 2026) and LLMail-Inject (Abdelnabi et al., 2025) extended evaluation to realistic web workflows and adaptive human attacks. Automated red-teaming

has since progressed from fixed templates toward adaptive search. AgentVigil (Wang et al., 2025a) and AgentXploit (Wang et al., 2025b) iteratively refine black-box injections, with AgentXploit using MCTS-guided seed selection; VeriGrey (Zhang et al., 2026) instead uses tool-invocation sequences as grey-box feedback for prompt mutation. AutoInject (Chen et al., 2026) and PISmith (Yin et al., 2026) learn attack policies, whereas SIRAJ, MUZZLE, and ChainFuzzer broaden search toward risk-oriented tests, injection surfaces, multi-step attacks, and source-to-sink tool chains (Syros et al., 2026; Wu et al., 2026; Zhou et al., 2026). Complementary defenses distinguish untrusted content through provenance marking, detect injections with learned guard models, or identify task-independent actions through masked re-execution, as exemplified by Spotlighting, PIGuard, and MELON (Hines et al., 2024; Li et al., 2025; Zhu et al., 2025). Despite this progress, most methods still optimize or evaluate attacks under predefined goals, surfaces, or success oracles; our work instead targets open-ended discovery of diverse vulnerability structures across an agent’s workflow. 

From attack optimization to vulnerability discovery. A smaller body of work moves toward system diagnosis. Know Your Agent uses black-box reconnaissance (Eliav et al., 2026) to construct target profiles for tailored exploitation, while PI-Hunter (He et al., 2026b) generates source-aware tests and analyzes execution trajectories to expose and localize vulnerable injection-ingestion paths. Our work builds on this shift but targets a broader and more fundamental problem: open-ended discovery of potential prompt-injection consequences and vulnerabilities in a target agent. Rather than treating the payload, injection point, or attacker task as the sole search object, we maintain an evolving model of the agent’s components, information and decision flows, state transitions, and observed vulnerabilities. This model guides hypothesis generation and consequence-path exploration across sources, tools, memory, and actions, producing evidence-backed explanations of how an injection becomes reachable, trusted, propagated, and consequential. 

## 3. ASPIRE 

ASPIRE aims to discover prompt-injection vulnerabilities in LLM agents as behavior-level failures. It treats an agent as an interactive system whose security depends on how information flows across external environments, reasoning modules, tools, and persistent state. This shifts red-teaming from optimizing isolated injection strings to uncovering hidden vulnerability pipelines: systematic paths through which external content influences agent decisions and causes unintended actions or state changes .

Problem setup. We consider builder-side vulnerability discovery for an LLM agent interacting with external environments and other components like tools and memory. 3.1. Static Reconnaissance and Search Space Construction 

ASPIRE starts with a static reconnaissance stage that analyzes the target agent before executing any red-team tests. The goal of this stage is to construct an initial behavior prior and search space. Given the agent specification, tool interfaces, and external environments, ASPIRE identifies the surfaces where untrusted content may appear, the tools that can retrieve such content, and the tools or state variables that can produce security-relevant consequences. This provides the initial structure for later behavior-guided discovery. Concretely, ASPIRE initializes both the behavior graph and the hypothesis space. It maps injection environments, such as mailboxes and calendars, to the access tools that retrieve their content; identifies action tools that may produce security-relevant consequences; and constructs candidate paths from these environments to downstream actions through the agent’s reasoning components (Figure 2). These paths form the initial behavior graph , which will be updated with evidence during future tests. From the same analysis, ASPIRE initializes candidate sets of consequences and injection methods. Candidate consequences are derived from writable tools, persistent states, and privacy-sensitive outputs, while candidate methods combine common manipulation tactics with context-specific strategies synthesized for the target agent. Together with the hypothesized behavior paths, these candidates define the initial search frontier from which the experts subsequently propose concrete skeletons. 

3.2. Behavior-Guided Vulnerability Discovery 

After static reconnaissance, ASPIRE performs vulnerability discovery through an iterative behavior-guided search loop. The key idea is to maintain an explicit behavior graph as the current security model of the victim agent, and to use this model to decide what to test. 

Behavior graph . The graph represents ASPIRE’s evolving belief about how attacker-controlled

information may propagate through the target agent. Its nodes capture injection environments, access tools, observations, reasoning modules, action tools, persistent states, and final outputs, while edges encode possible information and control flow between them. An action-oriented path takes the form:

where content from environment 𝐸 is retrieved, enters the agent’s observation, influences planning, and reaches an action or state change. Response-only paths instead terminate at the response generator and final output. Each edge maintains execution evidence and an evidence-derived status, allowing the graph to distinguish untested, supported, blocked, conditional, and saturated routes. Figure 2 illustrates a hypothesized path from a calendar injection through calendar.read and the planner to email.send or persistent memory. Execution evidence supports retrieval in 4/4 tests and reaches email.send in 2/4, while the confirmation-guard route is blocked and the memory branch remains untested. These distinctions guide the experts toward promising and unresolved paths. 

Red-team loop . At the beginning of each round, ASPIRE compiles the current graph into a security state describing supported paths, blocked or saturated transitions, conditional edges, reachable consequences, promising but unconfirmed triples, and recently observed failure modes. Two com-plementary experts use this state to determine what to test next. The Explore expert expands the discovery frontier by targeting unconfirmed consequences, under-tested environments, and uncertain behavior paths. The Exploit expert verifies and generalizes promising regions by completing partial trajectories, reproducing confirmed vulnerabilities, and testing whether they transfer across paths, environments, or methods. Both experts propose a batch of consequence-centric test skeletons, 𝑧 = (𝐶, 𝑀, 𝐸 ), based on the candidate paths and evidence maintained in the behavior graph. Separating these skeletons from concrete payload construction allows the experts to focus on the high-level decision of which security hypothesis should be tested next. Payload realization, by contrast, must account for the selected environment, trigger workflow, tool schema, and target consequence. This separation prevents the search from collapsing into local prompt rewriting and enables ASPIRE to reason over vulnerability coverage in terms of consequences, methods, environments, and their associated behavior paths. Then the realizer constructs an executable test 𝑥 = (𝐶, 𝑀, 𝐸, 𝑇, 𝑃 ), where 𝑇 is a benign user query, and 𝑃 is the injected payload placed in environment 𝐸 . The query is designed to activate a normal agent workflow involving the target environment, while the payload instantiates the selected injection method in a surface-native form. For example, a skeleton targeting an unauthorized email consequence through a calendar-action-item mechanism would be realized by placing a crafted action item in a calendar event and issuing a benign request such as asking the agent to review the user’s schedule and handle follow-ups. ASPIRE then executes the realized test against the victim agent and evaluates the resulting trajec-tory via a hybrid validation procedure. Rule-based checks determine whether the target consequence is actually realized, such as whether the relevant tool is called with grounded arguments and whether the expected external side effect occurs. An LLM evaluator assists with ambiguous responses and complex trajectories by extracting evidence and diagnosing why a test stalled. Importantly, Vulnera-bilities are confirmed only when the rule-based gates are satisfied and the observed trajectory links the injected content to the target consequence. Beyond a binary outcome, the evaluator decomposes each trajectory into intermediate signals, such as retrieval, planning, target-tool invocation, and effect realization, thereby localizing where an unsuccessful test stalled. ASPIRE uses evidence to update the behavior graph, refining reachable paths and blocking failed transitions. The updated graph guides the next round of hypothesis generation, forming a loop of proposal, realization, execution, and evidence-driven refinement.

3.3. Evidence-Based Vulnerability Consolidation and Mapping 

A successful payload alone provides limited insight into an agent’s security. Developers also need to understand how the injection propagated, why the agent failed, and whether the discovered case reflects an isolated exploit or a broader vulnerable region. To support such diagnosis, ASPIRE consol-idates the behavior graph, execution trajectories, and evaluator feedback into two complementary artifacts. 

Vulnerability report . For each confirmed vulnerability, the report reconstructs the evidence chain from the injection environment to the target consequence. It records the behavior path, injection method, consequence, and supporting evidence, including retrieved content, tool calls, arguments, outputs, and realized side effects. It also attributes the failure to behavioral causes such as source– instruction confusion or unsafe construction of sensitive tool arguments. The result is not merely a successful attack string, but an auditable account of how and why the vulnerability occurred. 

Vulnerability map . While each report explains an individual failure, the map reveals the broader structure of the explored attack surface. It organizes tested combinations of consequences, methods, environments, and behavior paths, distinguishing confirmed vulnerabilities from partial, failed, and untested hypotheses. Failed attempts are not treated as proof of security; instead, their stall points indicate where influence was interrupted and where further testing remains necessary. Together, the report and map turn isolated attack successes into actionable security knowledge: the report explains each vulnerability, while the map shows its position within the agent’s broader vulnerability space. 

3.4. Cross-Run Strategy Memory for Self-Improvement 

Concrete attack tests often transfer poorly across agents, but the decisions that made a search succeed or fail can remain useful. ASPIRE therefore stores transferable guidance on how to navigate vulnerability discovery , for example, when to switch injection surfaces, repair a trigger, compare methods, or abandon a saturated route, rather than payloads to replay. Each memory item contains five components: a category identifying the decision dimension, a polarity marking the experience as productive or cautionary, a context specifying when it applies, a claim summarizing the observed lesson, and an action recommending how the expert should respond. The central challenge is that useful decision knowledge is sparse within a long search trajectory. Instead of summarizing the trajectory indiscriminately, ASPIRE extracts turning points : decisions that materially advance, redirect, or stall the search. It first compresses the trajectory into a decision-focused digest, then identifies moments such as recovery after switching surfaces or repeated failures along an exhausted route. Each lesson is grounded in the preceding search state, chosen action, decomposed outcome, and resulting coverage change, helping separate transferable strategies from coincidental successes. Before each expert decision in a later run, ASPIRE retrieves memories relevant to the current graph state, failure stage, and candidate tests. Because prior experience may conflict with evidence from the new target, retrieved recommendations are adapted rather than followed directly: they may be retained, weakened, or suppressed according to local evidence. The resulting strategy brief indicates which candidate types to prefer, softly avoid, or allow as exceptions. Memory thus provides a context-sensitive prior over valid search choices, while the behavior graph remains the primary source of evidence about the current agent. ## 4. Experiment 

We evaluate whether ASPIRE can systematically discover diverse prompt-injection vulnerabilities across application domains, agent architectures, and red-team model backbones. 

4.1. Settings Benchmarks. We conduct experiments on AgentDojo (Debenedetti et al., 2024) and AgentDyn (Li et al., 2026), which provide diverse executable agent environments such as banking, travel and Github. Since ASPIRE is an open-ended agentic vulnerability discovery method, we only adopt their environment for evaluation. 

Baselines. We compare ASPIRE with AgentXploit (Wang et al., 2025b), a black-box prompt-injection fuzzing method, and VeriGrey (Zhang et al., 2026), a grey-box method guided by tool-invocation sequences. We also implement an Free-form agentic attacker , which allows a general-purpose attacker agent to autonomously probe and revise tests against the sandboxed victim without ASPIRE’s behavior graph or structured search policy. We follow the original configurations of published baselines whenever applicable; note that while baselines only optimize payloads against static user tasks, ASPIREmodels the full red-team tests by jointly instantiating benign user triggers and structured payloads. 

Victim agent architectures and model backbones. We consider victim agents based on ReAct (Yao et al., 2023) and planner–executor, representing integrated and separated planning–execution workflows, respectively. We use Gemini-3.7-Flash (Google, 2025) as the primary victim backbone and report additional backbones in Appendix B. To assess sensitivity to the red-team model, we instantiate ASPIRE and baselines with diverse models including Gemini-3.7-Flash, GPT-5.6-luna (OpenAI, 2026), Gemini-3.5-Flash-Lite, and DeepSeek-V4-Flash , under the same red-team protocol. 

Evaluation metrics. We report attack success rate (ASR) , defined as the fraction of executed tests that realize their intended malicious consequences. Since a high ASR may result from repeatedly exploiting the same weakness, we additionally measure discovery diversity and coverage . We treat each distinct consequence–mechanism–environment triple (𝐶, 𝑀, 𝐸 ) supported by at least one successful test as a unique vulnerability. Accordingly, our primary coverage metric, # (𝐶, 𝑀, 𝐸 ),measures the number of unique vulnerabilities discovered. We further report the numbers of unique consequences (#𝐶 ), injection methods (#𝑀 ), and injection environments (#𝐸 ) represented among successful tests. 

Implementation details. Each ASPIRE run consists of eight rounds. In each round, the Explore and Exploit experts propose up to eight test skeletons each. We use the same target configurations and environments across methods.

Impact of Behavior Graph and Experts. 

As shown in Table 4, we evaluate the neces-sity of the behavior graph and the expert guid-ance. 4.4. Additional Analysis 

In this section, we provide additional analysis on ASPIRE, including its performance under explicit defenses, its novel vulnerability discovery, and efficiency analysis. 

Red-teaming under active defenses. Ultimately, ASPIRE provides agent builders with actionable, evidence-backed vulnerability mappings, paving the way for principled and structural security measurement in real-world autonomous agent deployments.

## C. Details of ASPIRE 

In this section, we provide more details of ASPIRE. 

C.1. Algorithm 

We provide detailed algorithm in Algo 1. 

C.2. More details on LTM 

ASPIRE uses long-term memory to improve how its experts make red-team decisions across runs. The key challenge is not simply to remember which tests succeeded, but to understand why a red-team strategy was useful and when it should be repeated . Concrete tests are often tied to a particular agent, environment, or tool interface. In contrast, strategies such as switching retrieval surfaces after repeated refusal, repairing an under-specified trigger, or abandoning a saturated route can transfer across settings. Learning such strategies from complete trajectories is difficult because useful strategy knowledge is sparse within a search trajectory: most test attempts provide routine evidence, while only a few decisions substantially change the direction or productivity of the search. ASPIRE therefore focuses on turning points : moments when a decision advances, redirects, or stalls vulnerability discovery. These may include recovering from repeated failures by changing the retrieval surface, or continuing to spend tests on an already characterized route. To expose these decisions, ASPIRE first compresses the raw trajectory into a decision-focused digest and then extracts turning points together with the preceding search state, available choices, selected action, decomposed outcome, and resulting coverage change. Linking each lesson to both the search axis that changed and its effect on coverage helps distinguish transferable decision patterns from coincidental successes. It also preserves the conditions under which a useful strategy may cease to apply.

The resulting memories are reused as contextual guidance in later runs. Before each expert decision, ASPIRE retrieves memories that match the current behavior graph, failure stage, and available candidate tests. Because even a relevant cross-run lesson may conflict with evidence from the current target, ASPIRE further adapts each recommendation to the local search state. Retrieved lessons are grounded in the current candidate set and may be retained, weakened, or suppressed according to their applicability conditions and recent evidence. For example, previous experience may discourage further method comparison after repeated refusal on one surface, while partial progress in the current run may justify completing the method boundary before switching away. The adapted memories are finally compiled into a short strategy brief indicating which candidate types to prefer, softly avoid, or allow as justified exceptions. Memory therefore acts as a prior over valid search choices rather than a hard controller: the behavior graph captures what ASPIRE currently knows about the target agent, while strategy memory captures how similar search situations have been navigated. This separation allows ASPIRE to accumulate reusable red-team expertise without blindly transferring agent-specific attacks.
