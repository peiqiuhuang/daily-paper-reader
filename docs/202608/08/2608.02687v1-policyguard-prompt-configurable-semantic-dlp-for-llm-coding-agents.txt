Abstract 

AI coding agents accept free-form natural language prompts that may inadvertently contain cre-dentials, personally identifiable information (PII), or proprietary business data. Existing data loss prevention (DLP) solutions rely on rigid regex patterns, model fine-tuning, or vendor-managed clas-sifiers with limited customizability. We present PolicyGuard , a pre-model interception framework that classifies user prompts using an LLM guided by a natural language policy file. Our key contribu-tions are: (1) the policy-as-prompt paradigm, where DLP classification criteria are defined entirely in a plaintext policy document editable by non-engineers without code changes or model retraining; (2) a sealed evaluation protocol with template-family-level data splits, hidden holdouts, and frozen test sets to rigorously assess generalization; and (3) a comprehensive empirical evaluation across 2,000 multilingual prompts demonstrating 96.5% effective block rate (EBR) with only 3.0% false positive rate (FPR) on a frozen test set of 927 prompts, and perfect 100% accuracy on a 217-prompt hidden holdout. Information-matched baseline experiments show that PolicyGuard’s natural lan-guage format significantly outperforms equivalent content in JSON format (McNemar χ2 = 31 .58 ,

p < 0.001 ) and dramatically outperforms zero-shot classification (Cohen’s h = 0 .915 ). Cross-model portability experiments demonstrate that the same policy achieves 86.4–96.5% EBR across four different LLMs without modification. The entire policy refinement process from initial draft to final version required approximately 15 minutes and 10 lines of additions, suggesting that semantic DLP for coding agents is accessible to organizations without dedicated ML expertise. 

# 1 Introduction 

The proliferation of AI coding agents (OpenAI Codex, GitHub Copilot, Claude Code) has transformed software development workflows. Developers routinely submit natural language prompts containing code snippets, configuration details, error messages, and architectural descriptions to these systems. However, this interaction pattern creates a significant data loss vector: developers may inadvertently include live credentials, customer PII, internal business data, or proprietary code in their prompts (Chen et al., 2021). Traditional DLP systems were designed for structured data flows (email attachments, file uploads, database exports) where sensitive content follows predictable patterns. These approaches fall short for coding agent prompts because: 1. Contextual sensitivity : Whether a string like sk-proj-abc123def456 constitutes a live cre-dential or a placeholder depends on surrounding context that regex cannot parse. 2. Multilingual content : Development teams operating across languages (English, Korean, Japanese, Chinese) generate prompts where sensitivity markers like daeoebi (confidential) or migongae (unre-leased) require semantic understanding. 3. Adversarial framing : Users may inadvertently or deliberately frame sensitive content as “just a test” or “hypothetical,” bypassing pattern-based filters. 1arXiv:2608.02687v1 [cs.CR] 3 Aug 2026 4. Rapid policy evolution : Organizational policies change frequently; retraining classifiers or updating regex libraries for each change is prohibitively expensive. Existing LLM safety classifiers such as Llama Guard (Inan et al., 2023), WildGuard (Han et al., 2024), and ShieldGemma (Zeng et al., 2024) address content safety but use fixed taxonomies that do not accommodate organization-specific DLP policies. These systems distinguish harmful from safe content along predefined categories (violence, harassment, self-harm) rather than the credential/PII/confidential-information categories relevant to enterprise DLP. We present PolicyGuard , a framework that fills this gap by intercepting user prompts before they reach the coding model and classifying them using an LLM whose behavior is entirely configured through a natural language policy file. Our approach requires no model fine-tuning, no regex main-tenance, and no vendor-specific integration. The policy file, a plain text document specifying categories, decision criteria, and few-shot examples, can be authored and refined by security engineers, compliance officers, or developers with no ML expertise. Our primary contributions are: • Policy-as-Prompt Paradigm : We demonstrate that DLP classification criteria can be effectively ex-pressed as natural language policy documents, achieving significantly higher accuracy than equivalent content in structured formats (JSON rubric). • Sealed Evaluation Protocol : We design and execute a rigorous evaluation with template-family-level splits, a hidden holdout set never exposed to the policy author, and a frozen test set evaluated exactly once after all design decisions are finalized. • Empirical Validation : We report results on 2,000 multilingual prompts across four models, six format conditions, and three sensitivity categories, with pre-registered statistical tests. • Practical Accessibility : We show that iterative policy refinement achieves convergence in approxi-mately 15 minutes of human effort, requiring only natural language edits. 

# 2 Related Work 

2.1 Traditional DLP Systems 

Pattern-based DLP systems such as Microsoft Presidio (Microsoft, 2019) and Amazon Comprehend use regex rules and named entity recognition (NER) to identify PII entities. These systems excel at detecting structured identifiers (credit card numbers, social security numbers) but fail on contextual sensitivity: they cannot distinguish a live AWS access key from a documentation example, nor can they detect that Korean text marked “internal only” constitutes restricted information. Detect-secrets (Yelp, 2018) focuses specifically on credential patterns using entropy analysis and regex; it achieves high precision on standard formats but misses novel or obfuscated credentials. 

2.2 LLM Safety Classifiers 

The emergence of open-weight safety classifiers represents a significant advance over rule-based sys-tems. Llama Guard (Inan et al., 2023) uses instruction-tuned models to classify content against a safety taxonomy; Llama Guard 3 (Meta AI, 2024) extends this to multilingual settings. WildGuard (Han et al., 2024) covers a broader range of safety categories with 7B parameters. ShieldGemma (Zeng et al., 2024) provides lightweight 2B-parameter classification. However, all these systems define fixed category tax-onomies at training time. Organizations cannot add categories like “unreleased product roadmaps” or “pre-announcement M&A targets” without fine-tuning, which requires labeled data, compute re-sources, and ML expertise. PolicyGuard addresses this by accepting category definitions at inference time through the policy file. 22.3 Prompt Injection and Adversarial Attacks 

Prompt injection attacks (Perez and Ribeiro, 2022; Greshake et al., 2023) represent both a threat to and a target of DLP systems. The Instruction Hierarchy approach (Wallace et al., 2024) establishes priority levels for instructions, while defensive approaches like signed prompts (Suo, 2024) attempt to authenti-cate legitimate instructions. In our context, prompt injection is one of three sensitivity categories (T3): we detect attempts to manipulate the classifier itself while also protecting against credential leakage (T1) and confidential information exposure (T2). Our policy includes explicit anti-injection instructions and examples, though we acknowledge this remains an active area of concern (Section 7). 

2.4 Privacy-Preserving Prompt Processing 

Recent work has explored transforming prompts before they reach the model. CAPID (Ponomarenko et al., 2026) applies context-aware PII detection at the document level; DYNTEXT (Zhang et al., 2025) dynamically anonymizes text while preserving task utility; Preempt (Roy Chowdhury et al., 2025) pro-poses pre-model sanitization pipelines. These approaches are complementary to PolicyGuard: where they modify prompts to remove sensitive content, we make a binary gate decision (allow/block/review) based on policy. A deployed system might combine both: PolicyGuard for gate decisions, with sanitiza-tion applied to prompts in the REVIEW category. 

2.5 Policy-Guided Classification 

The idea of using natural language to configure classifiers connects to work on prompt engineering for classification tasks (Wei et al., 2022; Brown et al., 2020). Constitutional AI (Bai et al., 2022) uses natural language principles to guide model behavior, demonstrating that detailed instructions can substantially shape model outputs. PolicyGuard extends this insight to the DLP domain, treating the policy file as the sole configuration interface for a binary classification system. 

# 3 System Design 

3.1 Architecture Overview 

PolicyGuard operates as a pre-model hook in the coding agent pipeline. When a user submits a prompt to a coding agent (e.g., Codex CLI), the hook intercepts the prompt before it reaches the primary model: 

User Prompt |v[Hook: UserPromptSubmit] |v[PolicyGuard Classifier] <-- policy.txt |+-- ALLOW --> Prompt proceeds +-- BLOCK --> Prompt rejected +-- REVIEW --> Queued for review 

The classifier is an LLM (in our primary configuration, gpt-oss-safeguard-20b hosted on Amazon Bedrock) that receives the policy file as a system prompt and the user’s original prompt as the user message. The model returns a structured JSON response containing a decision and applicable categories. 33.2 Policy File Format 

The policy file is a plain text document with four sections: 

INSTRUCTIONS : Output format specification and anti-injection directives. The classifier is in-structed to treat the user message purely as content to classify, never following instructions embedded within it. 

POLICY : Category definitions specifying what constitutes sensitive content. Our reference policy defines eight categories: AUTH SECRET , FINANCIAL IDENTIFIER , GOVERNMENT IDENTIFIER , PER -

> SONAL DATA

, CUSTOMER CONFIDENTIAL , PROPRIETARY CODE , PROMPT INJECTION , and OTHER SENSITIVE .

DECISIONS : Decision criteria mapping conditions to ALLOW/BLOCK/REVIEW outcomes. These criteria encode organizational policy; for example, that test credentials following real formats should be blocked, or that Korean restriction markers trigger blocking regardless of surrounding content. 

EXAMPLES : Few-shot demonstrations providing concrete input-output pairs. Our final policy contains 12 examples spanning all three decision types and multiple languages. The complete policy file is 106 lines (approximately 1,200 tokens), fitting comfortably within any modern LLM’s context window while remaining human-readable and editable. 

3.3 Fail-Closed Design 

PolicyGuard implements a fail-closed architecture: any error condition results in BLOCK: • Timeout : If the classifier does not respond within the configured timeout (default: 10 seconds), the prompt is blocked. • Parse failure : If the response is not valid JSON or does not contain a recognized decision, the prompt is blocked. • API error : Network failures, authentication errors, or service unavailability result in blocking. • Ambiguous output : If the model produces an unrecognized decision value, BLOCK is applied. This design reflects the threat model: a missed detection (false negative) has higher cost than a false alarm (false positive), as the former results in irreversible data exposure while the latter merely inconveniences the developer. 

3.4 Classification Output 

The classifier returns exactly one JSON object: 

{"decision":"ALLOW|BLOCK|REVIEW", "categories":["CATEGORY_NAME"]} 

The categories array is empty for ALLOW decisions and contains one or more applicable cate-gory names for BLOCK/REVIEW decisions. This structured output enables downstream logging, policy violation analytics, and category-specific alerting. 

3.5 Iterative Refinement Protocol 

A key design principle of PolicyGuard is that classification performance is improved exclusively through policy file edits, requiring no code changes, model retraining, or infrastructure modifications. The re-finement protocol proceeds as follows: 1. Initial authoring : Write policy v0 referencing the development set for category definitions and edge cases. 2. Validation evaluation : Run the policy against the validation set; identify misclassified prompts. 43. Error analysis : Categorize errors and draft targeted policy additions. 4. Policy edit : Add or modify decision criteria, examples, or category definitions. 5. Re-evaluation : Re-run on validation set; confirm improvements without regressions. 6. Convergence : Stop when validation EBR improvement is less than 1% for two consecutive iterations. 7. Freeze : Lock the policy file; no further edits permitted. 8. Sealed evaluation : Evaluate once on hidden holdout and frozen test set.

4.4 Metrics 

Primary endpoints (pre-registered): • Effective Block Rate (EBR) : (BLOCK +REVIEW )/total should block. Measures the system’s abil-ity to prevent sensitive content from reaching the downstream model. • False Positive Rate (FPR) : wrongly blocked /total should allow. Measures developer inconvenience from legitimate prompts being rejected. 

Secondary endpoints : Overall accuracy, per-category recall, latency P50/P95, format adherence rate. 

4.5 Statistical Analysis Plan 

All statistical tests were pre-registered before the sealed run: • C1 vs C2 (format effect) : McNemar’s test for paired nominal data. • EBR > 90% (sufficiency) : One-sided exact binomial test. • FPR upper bound : Wilson score 95% confidence interval; claim supported if upper bound < 5% .• Effect sizes : Cohen’s h for proportion comparisons. • Multiple comparisons : Holm–Bonferroni correction applied to all pairwise model comparisons. 64.6 Evaluation Protocol 

The evaluation followed a strict sealed-run protocol: 1. Phase 0 : Dataset generation with multi-label annotation (2 annotators + adjudication), template-family-level splitting. 2. Phase 1 (Pilot) : 100-prompt pilot on validation subset to verify infrastructure and confirm power calculations. 3. Phase 2 (Refinement) : Iterative policy improvement on validation set only. Holdout and test never accessed. 4. Phase 3 (Freeze) : Policy, evaluation code, and analysis scripts frozen. Policy hash recorded: c590f5cb... .5. Phase 4 (Sealed Run) : All predictions generated in a single session. No post-hoc modifications permitted.

Training distribution alignment : LLMs are predominantly trained on natural language text. 6.2 Model Selection Trade-offs 

The cross-model results reveal a multi-dimensional trade-off space: • M1 (20B, specialized) : Best overall performance but highest latency among hosted options. • M3 (Ministral 8B) : Surprisingly strong (92.1% accuracy) with the lowest latency (350ms) and perfect format adherence. • M4 (Claude Haiku 4.5) : Lowest FPR (1.8%) with good accuracy (93.5%), suitable for environments where false positives are particularly costly. • M2 (Llama 3.1 8B) : Poor performance despite similar parameter count to M3, suggesting model architecture and instruction-tuning quality dominate.

With 34% Korean, 3% Japanese, and 3% Chinese prompts in our dataset, PolicyGuard demonstrates multilingual capability primarily through explicit policy rules. The Korean restriction marker rule was the single most impactful addition during refinement, suggesting that multilingual DLP requires ex-plicit enumeration of language-specific sensitivity indicators rather than relying on the model’s general multilingual understanding. 

# 7 Limitations 

We acknowledge several limitations: 

Synthetic evaluation data. Our 2,000-prompt dataset is synthetically generated, as real enterprise 12 coding agent logs are unavailable for research due to the very privacy concerns this system addresses. While designed to be realistic, the distribution may not perfectly reflect production environments. 

Single-turn classification. PolicyGuard classifies each prompt independently without access to conversation history. Sensitivity may be established across multiple turns. 

Model dependency. Performance varies significantly across models (64.1–96.5% EBR), and orga-nizations must validate on their chosen model. 

Adversarial robustness. We have not conducted a dedicated adversarial red-teaming exercise against the classifier. A motivated attacker with knowledge of the policy structure could potentially craft inputs that evade detection. 

REVIEW category semantics. Our EBR metric counts REVIEW as blocked (operational policy). In our results, the REVIEW rate is low ( < 2% ), so this does not materially affect conclusions. 

Format adherence. Format adherence for M1 was 89.9% (834/927), meaning ∼10% of responses required fallback parsing. 

# 8 Conclusion 

We have presented PolicyGuard, a framework for pre-model data loss prevention in LLM coding agents that uses natural language policy files to configure classification behavior. Our sealed evaluation demon-strates that: 1. Natural language policies are effective : PolicyGuard achieves 96.5% EBR with 3.0% FPR on a 927-prompt frozen test set, significantly exceeding the 90% EBR threshold ( p = 0 .000002 ) and satisfying the FPR < 5% constraint (95% CI upper bound: 4.8%). 2. Format matters : The natural language format significantly outperforms JSON formatting (McNe-mar p < 0.001 ), with a small–medium effect size ( h = 0 .260 ). 3. Policies are portable : The same policy achieves 86.4–96.5% EBR across four LLMs without modi-fication. 4. Iteration is rapid : Policy refinement required approximately 15 minutes and 10 lines of natural language additions. These results suggest that the policy-as-prompt paradigm is a viable approach to configurable DLP for LLM-based development tools. As coding agents become ubiquitous in enterprise environments, lightweight, auditable, and rapidly-configurable privacy gates like PolicyGuard will be essential compo-nents of the security stack. 

Future work includes: (1) multi-turn context modeling for session-level sensitivity tracking; (2) ad-versarial red-teaming and policy hardening; (3) user studies with security practitioners; (4) integration with prompt sanitization systems; and (5) scaling evaluation to production traffic volumes.
